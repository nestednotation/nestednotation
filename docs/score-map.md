# Score Map — Requirements & As-Built Notes

Status: **experimental** (owner: "just give it a try, I might remove it later"), built on `feat/session-lines-v2`. This doc is the context for continuing (or removing) the feature.

## Context & purpose

A live, git-graph-like visualization of an entire score — main flow plus every sub-score — so the operator can **track where the room is** during a session: which frame each line sits on, who is parked at a barrier, who dived into a sub. It doubles as the **rewind control**: click or tap a frame — in a session-lines room, a frame of a common-checkpoint track group → "rewind ROOM", any frame in a line's trail (main flow or its current sub dive) → "rewind L*n* here", a previously executed split frame → "undo split" (collapse its live descendant subtree back into the original parent), and a frame lines merged at → "undo merge" (put each of them back where it stood, devices and all — for any merge of the session, taking off whatever the room built on top of it first); on a vanilla score, a visited frame → per-step "rewind here" (the single playhead is the room). Works for **every score**: a vanilla score (no `session-*` markup) is presented as a **single-line session** (owner decision).

## Locked design decisions

1. **Standalone page**, not embedded in the session view: `GET /session/:id/map?p=<adminPassword>` renders [views/session-map.jade](../views/session-map.jade). (First iteration was an overlay panel inside the session page; owner asked for a separate view.) The session page's only tie is a dynamic "map ↗" link in the admin footer.
2. **Zero cost to vanilla behavior.** The relationship graph is now built for _every_ score in `buildSVGContent` (it always was — only the assignment was gated), but: it is never persisted (`toJSON` allowlist), all orchestration still gates on `hasSessionLines`, per-line message payloads (`payload.lines`) remain session-lines-only, and the map page/routes are rendered live (never baked into the apicache-shared session HTML). Vanilla baseline stays byte-identical.
3. **The map is an observer plus thin rewind triggers.** Session-lines rooms have five rewinds, all riding `MSG_SELECT_HISTORY` and told apart by payload shape (the IMPLICIT bound-line `{selectedIdx}` jump is retired and refused server-side): **room-wide** `{group}` — recompute a common track-group checkpoint and move every non-retired line; **line-targeted** `{lineId, selectedIdx, frame}` — move one named line within its active trail; **structural split undo** `{splitEventId, frame}` — recursively retire every live descendant of that persisted split instance, restore its original parent at the split frame/history, and rebind all connected/offline devices to it; **structural merge undo** `{mergeEventId, frame}` — separate a rejoin again: each absorbed line returns to the frame it was standing on, with the devices it carried, and the survivor to its own; and **roll a line back out of its dive** `{lineId, exitSub: true, sub}` — land one line on any main-flow frame it has already visited, defaulting to the frame it dived from. A nested split undo leaves unrelated lines and the room's reached registry/`latestGroupArrival` untouched, and so does a merge undo. A later merge wholly inside a split's subtree is safe; a merge crossing the subtree boundary blocks that split undo because the populations can no longer be separated without per-device ancestry — undoing the merge itself lifts that block, so the menu offers such a split again whenever the crossing merge is still active (the undo takes it off on the way); only once a room checkpoint rewind has EXPIRED that merge is the block permanent. On a vanilla score the menu still sends `{selectedIdx}` — the single playhead IS the room.
   **Observer means not population (owner decision):** the page sets `window.wsMapView = true`, ws-client puts `mapView` on every envelope, and the server tags the connection `isMapView` at `MSG_PING`. Map connections are excluded from player/rider counts, group/hold-until waits, attrition, dormant revival, adoption parking, split membership and line balancing (`performerLineConnections` in [routing.js](../lib/session-lines/routing.js)) — a line holding only map tabs goes dormant like an empty one. They keep a line binding solely so history/graph payloads can be addressed to them. (Admin _session-page_ connections DO count — L3: an admin is a player with extra tools.) A **rider** — a session page opened with no password — is the other observer (owner): it is excluded from the same waits, tallies, attrition and balancing, is never bound to an inactive line, and is re-homed when the line it watches goes dormant. Unlike a map tab it still appears in the badge counts, because the operator wants to see the audience (see [session-lines.md](session-lines.md) #12).
4. **Vanilla = one line.** With no `lines` payload available, the single playhead is tracked client-side from the broadcast `MSG_SHOW` (`showIdx` → `graph.frames[i]`; `-1` = paused placeholder, marker cleared) and room player/rider counts from the vanilla `MSG_SHOW_NUMBER_CONNECTION`.
5. **Rendering via CDN** (cytoscape + dagre + cytoscape-dagre from jsdelivr — the app already depends on jsdelivr for howler/qrcode). If dagre fails to load, fall back to cytoscape's built-in `breadthfirst` layout; if cytoscape fails, the map doesn't render (page + everything else unaffected). No internet ⇒ no map.
6. **Manual arrangement is client-local.** Nodes are draggable; positions persist in `localStorage` (`mapPos:<sessionId>:<scoreFolder>`) and re-apply after the automatic layout on reload. The key carries the **score** as well as the session because the SM can repoint a session at a different folder: under a session-only key the frame names the two scores happen to share (`START.svg`…) came back at the old score's coordinates, dragged on top of the new layout. A header **re-layout** button discards them and re-runs dagre. Live updates never move nodes.
7. **Admin gating is by ws signature, not by page access.** The page renders for anyone with the URL; the live feeds (`lines`, history) only flow when `p` matches the admin password, because the server addresses those messages to admin connections only. Wrong `p` ⇒ static graph, no badges/trail, rewinds silently refused server-side.

## Architecture

### Server (all additive)

- **`GET /session/:id/graph`** ([routes/session.js](../routes/session.js)) → `{ main: session.graph, subs: { <score>: subGraph } }`. 404 only when the session is missing or its graph hasn't been derived yet. **Deliberately uncached**: `session.graph` is re-derived asynchronously after boot, and apicache (which caches 404s) once wedged the map for a full 30-minute TTL from one boot-window fetch.
- **`GET /session/:id/map`** → validates `?p=` against the session admin password and returns a clear `403 Admin password invalid or expired` before rendering when it fails. Authorized requests render `session-map.jade` live (never cached/baked). Locals: `sessionId`, `scoreTitle`, `wsPath` (now exported from [database.js](../database.js)), and **all `MSG_*` constants as one JSON blob** (`constantsJson`). The blob matters: jade renders the view from disk per request while route code lives in the booted process, so a per-constant local missing from a stale process rendered `window.X = ;` — a SyntaxError killing the whole inline script. The blob degrades to a caught runtime error instead.
- **Graph always assigned** ([database.js](../database.js) `buildSVGContent`): `this.graph = sessionGraph` for every score; `hasSessionLines`/`frameLinks` stay gated on markup.
- **Score changes under the map** ([routes/sm.js](../routes/sm.js), `update-session`): swapping the session's folder already broadcast `MSG_CHANGE_FOLDER`, and so does stopping the session. An update that leaves the folder alone rebuilds the score **in place** (the operator edited the frames on disk) and used to tell nobody — the session pages kept their injected frames and the map kept the graph it fetched at load, until someone hit _global refresh_. It now broadcasts the same `MSG_CHANGE_FOLDER`, gated on `session.contentHash` (a sha256 accumulated over the frames in `buildSVGContent`, not persisted) actually changing across the rebuild — so a parameters-only update (hold/vote duration, voting size, volume) still reloads nobody mid-performance.
- **Structural projections are memoized and transported in two tiers** (`structuralProjection` in [bin/www](../bin/www)). `splitRewinds`, `mergeRewinds` and `absorbedLines` are each quadratic in the number of structural events — a plan, a chain walk and a convergence grouping per event — so the result is cached by score/topology/line identity. Normal admin tabs now receive only the ordinary room counts and compact live-line status they display. Map tabs additionally receive checkpoints, a compact event summary and a structural version; full cascades, restored line IDs, landings and ghost trails are requested once when that version changes. Broadcast JSON is encoded once per recipient class. This removes the former 1.4 MB (100 passages) / 5.7 MB (200 passages) structural body from every landing, join and leave push while keeping topology-changing redraws exact. Persisted `undone` events are omitted, and legacy `expired` events retain only identity plus the trail evidence still required by rewind blocking and barrier corroboration.
- **Live positions**: `payload.lines[]` (admin-only, session-lines scores) gained `sub` — the top-of-stack sub-score name — so the client can address `sub:<score>:<frame>` nodes, `subReturn` — where an eject would drop that line (the outermost dive's return frame, resolved against the live list; null when the score no longer offers it) — and `subOrigin`, where a rollback would put it back (the frame it dived from, same null rule). `afterLineArrived` is wrapped (`afterLineArrivedInner` + `finally`) to call `updateNumberOfConnectionForSession(session)` after **every landing**, so admins get a positions snapshot on each frame advance / dive / return / split / merge, not just on connect/close. Vanilla messages untouched.

### Client ([public/javascripts/session-map.js](../public/javascripts/session-map.js) — the page's only script besides ws-client.js)

Reuses [ws-client.js](../public/javascripts/ws-client.js) wholesale (reconnect/backoff, visibility recovery, time sync) by implementing its `parseMessage` contract:

| message                                    | map reaction                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MSG_PING`                                 | 3-ping time calibration mirroring session.js (shares ws-client's top-level `let`s), then `MSG_NEED_DISPLAY` — whose admin reply chain includes history + a positions snapshot                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `MSG_SHOW`                                 | `window.currentIndex` tracked (rides as `cid`); in vanilla mode = the single line's position                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `MSG_SHOW_NUMBER_CONNECTION`               | Regular map push: `lines[]` → per-line badges/history overlay, `roomCheckpoints[]`, compact `structuralEvents[]`, and `structuralVersion`. When the version changes the map requests a detail push (`structuralDetails:true`) containing `splitRewinds[]`, `mergeRewinds[]`, and `absorbedLines[]`. Ordinary admin tabs receive counts plus `lines[]`, but no structural fields; absent `lines[]` + vanilla mode synthesizes the one line from those counts.                                                                                                                                                                                                                                                            |
| `MSG_SELECT_HISTORY`                       | `{history, selectedIdx}` — vanilla-mode trail overlay + per-step rewind menu state (`available` is ignored). Outbound: `{group}` = room checkpoint, `{lineId, selectedIdx, frame}` = targeted line, `{splitEventId, frame}` = structural split undo, `{mergeEventId, frame}` = structural merge undo (session-lines), `{selectedIdx}` = vanilla jump                                                                                                                                                                                                                                                                                                            |
| `MSG_BEGIN_VOTING` / `MSG_BEGIN_HOLDING`   | **vanilla mode only**: the room's voting/holding phase, cleared client-side at `endTime` (server sends no "ended" message) or on the next `MSG_SHOW`. Session-lines mode ignores these (they address the map's own bound line) — every line's `voting`/`holding` flags ride in the `lines[]` payload, which the server re-pushes on vote-window open, hold expiry, group-stay resolution, and the SM global-hold toggle (landings/rewinds already pushed)                                                                                                                                                      |
| `MSG_CHANGE_FOLDER` / `MSG_GLOBAL_REFRESH` | `location.reload()`. Everything the page draws is derived from the score — the `/graph` fetch, the title, the saved arrangement — so it reloads the way the session page does rather than patching the pieces. Both constants are read `window.`-qualified: `session-map.js` is served from disk while the constants blob comes from the booted process, so against a **stale server** (one started before these two were added to the `/map` route) they are simply `undefined` and never match — the symptom is a map that keeps drawing the old score, and the fix is a server restart, not a client change |
| anything else                              | ignored (addressed to the map connection's line; irrelevant)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Visual vocabulary** (cytoscape classes):

- Nodes: `start` (green border), `split` (orange), `barrier` (red octagon), `substart` (blue diamond — a frame carrying ≥1 `session-sub-start` link), `subend` (double border), sub-score frames grouped in dashed `subbox` compound nodes.
- Track groups: `grouped` nodes get a per-group pastel fill (stable palette, sorted group names over main + subs, cycles past 8 groups) and a `⟨group⟩` label line under the frame name. The palette avoids the state hues (amber/green/grey), and state fills (`here`/`visited`/…) deliberately override the tint — the label line keeps the group readable meanwhile.
- Edges: plain hrefs (grey), `split-edge` (orange), `merge-edge` (purple, = href that is also its source's `rejoin-at` target), `dive`/`return` (blue dashed/dotted, one pair per `session-sub-start` link), `waits` (red dotted, barrier → hold-until target, sub-qualified `score/frame` refs resolve into subboxes), `via-sub` (dotted grey — a sub link's href, i.e. its return landing, walked only after the sub).
- Live: `here` (yellow) with badge `L0·2p+1r⏳` (players + riders — riders are audience: counted here, never population; ⏳ = parked at barrier; ⏩ = a waiting barrier — a track group's arrival wait or a hold-until — is held open _for_ this line, and its node menu offers the advance; 💤 = its stalest device has sent no app-level message for 3 min, i.e. a socket whose page may be gone — see session-lines.md §10; **admins count as players** — an admin is a player with extra tools — but **map tabs count nowhere at all**: a `/map` connection binds to a line only so the server can address it, and is excluded from every count, tally, membership and persisted record in the room), `here-waiting` (red border), `here-dormant` (grey).
- Frame lifecycle on the occupied node: `here-voting` (purple dashed border + ✅ badge glyph — a voting window is open) and `here-holding` (teal border + ✋ glyph — the frame's holding period is running). Mutually exclusive in practice; declared before waiting/dormant so those still win the border/fill.
- **A still-undoable split or rejoin carries a `⏪⏪` badge** — the one badge that is not about a line standing here. A merge point stays reachable for the whole session (session-lines.md §8.4), but the rejoin FRAME itself carries no marking of its own — so the only way to reach an older rejoin was to remember which frame it was and click it. (When this was written the ghosts came off an older passage as well, which left it with nothing on the canvas at all; its routes are now drawn like any other offered passage, and the badge marks the frame they converge on.) Written through `data("badge")` rather than a new class, which keeps it clear of the four border colours a node can already carry.
- History: `visited` (green tint), `visited-ahead` (pale, redo entries), `checkpoint` (blue underlay halo). Session-lines mode paints these from `lines[].trail`/`checkpoint` — EVERY line's trail (visited = union over lines, sub trails resolve into their subbox) and one halo per line (normally coinciding with its `here` node, since a landing moves the pointer to the end) — so a synced room shows a halo on each frame of the track group, per-line answers to "what is the room's checkpoint". The bound line's `MSG_SELECT_HISTORY` drives the vanilla-mode rewind MENU and paints the overlay only in vanilla mode / before the first lines push (`visited-ahead` is defensive there — `setCurrIdxTo` truncates redo entries on a jump, so in practice the pointer always sits at the trail's end).
- **Ghost routes**: while a merge can still be undone, **every route that fed it** is painted — `ghost-trail` (pale grey fill + dashed grey border) over the trail its undo would give each line back, and `ghost-landing` (grey underlay halo) on the node each would land on. The routes of the lines it swallowed ride a separate `absorbedLines[]` payload array, because those lines are retired: they are in no count, no line panel and no `lines[]` entry. **The SURVIVOR's own pre-merge route is ghosted with them** (owner: "all lines should be equal … the map has no main line, it only lines") — it rides the merge entry as `survivorTrail`/`survivorLanding`/`survivorSub`, built by the same `absorbedRoute` helper off the OLDEST member of the convergence, which is the position the whole passage's undo restores it to. Before that the survivor's route was live green history and its co-arrivals' were ghosts, and which route got the green was decided by nothing but `planRecombine` electing the lowest-numbered line as survivor — so `L0` won every merge it was in and read as a main line the model does not have. Behind a still-undoable rejoin nobody is standing on any of these routes and one undo gives all of them back, so they now read alike, and a line's green history begins at the rejoin frame. A live line still wins a node it SHARES with a ghost (ghosts are painted first, then their trail class is removed from anything a live trail covers) — with the one exception of that line's own pre-merge frames, which is what keeps the survivor's route dashed; another line visiting one of them still turns it green. All of it vanishes the moment the merge expires, and the survivor's history goes back to green. “Still undoable” is asked of the merge ENTRY — `mergeRewinds[].available`, the same answer the menu is built from — rather than re-planned per event: a plan refuses anything the room has built on since (`superseded`), so the routes into an older rejoin went undrawn while its `⏪⏪` badge offered the undo one click away. That covers pair-merges (the older half of one convergence always reads superseded alone) and stacked rejoins (a second convergence on a later frame) with one test, which is what a room that forks three ways and rejoins twice needs: three routes in, three ghosts. **A ghost has to look like a ROUTE**: the old `#eceff1` fill differed from the `#f4f4f4` of a frame nobody has ever walked by a dashed border alone, so at map zoom the routes an undo could still be reached along read as blank score. The fill is `#cfd8dc` now, the label is dimmed, and every hop whose BOTH ends are still ghosts after the live pass gets `ghost-edge` — one dashed grey path, declared last so it wins over the structural edge colours along that stretch. Asking the classes rather than the trails keeps it honest for free: a node another line has since walked onto is green again, so the edges either side of it stop being ghosts with it. The final hop INTO the rejoin is never ghosted — its target is the node a line is standing on — so the purple rejoin arrow still says where the passage ends.

**Legend**: the vocabulary above is a dozen encodings the canvas never explained anywhere the operator could see, so the header carries a `? legend` toggle opening a pinned corner panel — a swatch and a line per encoding, grouped as routes / where the lines are / where they have been / frame kinds / badges / what a menu entry's ⏪ or ⏪⏪ means (the single/double glyph is the difference between moving one line inside its own trail and changing the room, and it was an encoding the menu used everywhere and explained nowhere). Written from the same colour values the cytoscape `STYLE` uses (change one, change its row); rows flagged `lines: true` are dropped in vanilla mode, where a single playhead paints no splits, rejoins, ghosts or per-line badges, and a heading left with no rows drops with them. Off by default and remembered per session in `localStorage` (`mapLegend:<sessionId>`), like the manual arrangement. Pinned over the canvas rather than in the flow, so opening it never reflows the graph out from under a pointer.

**Node menu** (`tap` on a node, covering mouse click and touch tap) — mode-split (the implicit bound-line rewind is retired). The live action comes first, the rewinds after it:

- **Session-lines, any node a straggler stands on**: "⏩ advance L*n* to ⟨_where_⟩" → `MSG_BARRIER_RELEASED {frame, advance: true, lineIds: [id]}`, the per-line half of the barrier strip's force-advance. `frame` is the barrier the line is holding open, taken from the admin `barriers[]` push that also names the destination: the exact frame for a hold-until (`advanceTargets`), the group name for a track-group wait (whose least-occupied frame is only picked when the command runs). A `Sub/Frame.svg` destination lands the line inside that sub-score (its device switches to sub view on `MSG_SUB_ENTER`), and the entry appears on the sub's own node too when the straggler is already down there. Where the score offers no landing at all the entry becomes a note saying so. Confirm-gated — it moves performers' devices. Where the line already stands on the target, the entry reads "⏩ end L*n*'s hold at ⟨…⟩", which is what the command does there.

- **Session-lines, rolling an in-sub line back**: → `MSG_SELECT_HISTORY {lineId, exitSub: true, sub, selectedIdx, frame}`, the eject's opposite — the line leaves the sub and lands on a frame it has already played, un-dived and free to take the sub again. Offered in two shapes. On **any main frame in that line's `mainTrail`**, one entry per occurrence: "⏪ rewind L*n* here (out of _Sub_)" — the destination-node grammar the map already uses for main-flow lines, except that the trail-END occurrence IS offered (the line is not standing there, it is down in a sub). On the **sub frame the line stands on**, beside the eject, a shortcut for the common case: "⏪ rewind L*n* to ⟨_dive origin_⟩" (`lines[].subOrigin`), which sends no `selectedIdx` and lets the server read the trail's own current entry. Each sub valve stands on its own destination: a dive whose return frame is gone can still be rolled back, which is exactly when that is the only move left. Confirm-gated; the line does NOT park at the landing (an operator rewind is authoritative), and everything after the chosen step is dropped from its trail.

- **Session-lines, sub frame a line stands on**: "⏫ eject L*n* to ⟨_return frame_⟩" → `MSG_BARRIER_RELEASED {eject: true, lineId, sub}`. Not a barrier resolution — it pops one line out of its dive onto that dive's own return landing, and unlike the advance above it is offered whether or not anything is waiting on the line, because a line stuck mid-dive stalls the room on its own. The destination comes from `lines[].subReturn` in the same push, so the entry names it before the operator commits; where the score no longer holds that frame the entry becomes a note saying the line cannot be ejected. Confirm-gated — it moves performers' devices (they leave sub view on `MSG_SUB_EXIT`). Ejecting restores the line's main-flow trail, so the rewind entries below become available on it immediately.

- **Session-lines, main-flow frame**: "⏪⏪ rewind ROOM to ⟨group⟩" when the frame's track group is a common checkpoint → `MSG_SELECT_HISTORY {group}` (confirm: every line moves to its own frame in the group, and how many rejoins made since that checkpoint come off on the way and which lines that puts back). **Which groups qualify, and which rejoins each would take off, are decided server-side** and pushed as `roomCheckpoints[] = {group, byLine, undoes}`. The map used to re-derive both with its own copy of `commonCheckpoints` over `lines[]`, and the copy could not agree with the server on either: it counted riders as population, so a line carrying only spectators hid a checkpoint the server would have accepted, and it could not see the split records, so a line whose trail a fork had truncated blocked every group the room crossed before that fork — and named none of its own rejoins in the confirm. `undoes` comes from the same `roomRewindPlan` + `mergesBehindRoomRewind` pair the click runs, so the confirm promises what the gesture does rather than a second guess at it. Plus one "⏪ rewind L*n* here" per PAST occurrence of the frame in each **main-flow** line's trail (the trail-end occurrence is the line's current position — skipped; in-sub lines are skipped too: rewinding their main trail would pull them out of the sub) → `{lineId, selectedIdx, frame}` (confirm: only this line moves). When neither applies, a note explains why ("not a room checkpoint yet — some line hasn't passed this group" / "only a line's current position here" where a line stands on the frame and its trail-end entry is all there is / "**no line's current trail reaches here**" where none does). That last one used to read "no line trail through here", which is a claim about HISTORY the map is in no position to make: a split truncates the trail it forks from (session-lines.md §6), so after a fork every frame the room played before it carries no line's trail at all — and the operator who watched three lines walk into that very frame was told nothing had. The undo for such a passage is reached from its rejoin node — or from any node its lines come back to: where the menu would otherwise be empty, an older passage's landings each carry "⏪⏪ undo the merge at ⟨*frame*⟩ — L*n* comes back here" (below). The room entry is also **disabled** ("room is at ⟨group⟩ — current position") when every line is already standing in that group: the per-line entries have always marked their trail-end that way, while the one gesture that expires every merge undo offered a live button for its own no-op.
- **Session-lines, an ABSORBED line's frame**: one "⏪⏪ rewind L*n* here — out of the merge at ⟨F⟩" per occurrence of the frame in the ghost trail of each line a still-undoable merge swallowed → the same `{lineId, selectedIdx, frame}` message, which `lineRewind` answers by undoing that merge (the whole convergence) and then walking this line on alone. Unlike a live line's entries the LAST occurrence IS offered: a ghost stands nowhere, so its trail end is the frame it came into the merge from and that entry is simply "bring it back where it was" — the undo lands it there and nothing else moves. The confirm names the merge, the lines that come back with it, and whether this one then moves further.
- **A refused rewind is reported**: all five entry points can turn a click away — a stale menu, a topology that moved — and the map alerts with the reason in plain terms (`MSG_REWIND_REFUSED`) instead of leaving the operator with an answered confirm and no effect. The room checkpoint rewind and the sub rollback joined the other three; both validate their whole plan before touching a line, so their refusals are clean no-ops. When a cascading undo stopped PART-WAY the alert says so (`moved`) rather than "Nothing moved": the steps it had already taken off cannot be put back. The lines snapshot is re-pushed with the refusal, so the menu the click came from is rebuilt behind the alert.
- **One act, one entry**: on the node a whole convergence lands back on, every entry above resolves to the SAME undo — the survivor's per-line rewind and each swallowed line's ghost each take the passage off and then walk their line nowhere — so the menu offered "⏪⏪ rewind L0 here", "⏪⏪ rewind L1 here" and "⏪⏪ rewind L2 here" for three identical outcomes, none of them named for what it does. `collapsedMergeLandingHtml` offers it once as "⏪⏪ undo the merge at ⟨F⟩ — L0, L1, L2 all come back here", firing the same `{mergeEventId, frame}` the rejoin node's own entry does, and returns to the per-line entries the moment anything at the node is a real rewind of its own (a line that would walk on afterwards, an earlier step of a ghost's route).
- **A rewind says what it did**: a refusal already answered back, but success said nothing — the operator answered a confirm promising a topology change and got a redrawn canvas to infer from. All five entry points now answer `MSG_REWIND_DONE {kind, frame}` too, and the map shows back the sentence its own confirm promised, held since the click (after the undo the entry is gone, so the receipt cannot be composed afterwards). A timed panel pinned over the canvas, not the header's status line — that is rewritten by every lines push, and a rewind sends several — and not an `alert()`: a refusal interrupts because the operator is waiting on an answer, a success only has to be seen. **Which answer belongs to which click is decided by an `operationId`** minted per gesture and echoed on both `MSG_REWIND_DONE` and `MSG_REWIND_REFUSED`. Kind + frame describe the EVENT, and two operator tabs can undo at the same frame a second apart — so that pair matched another tab gesture and showed its promise back as this one. With the id, the tab that clicked reads its own sentence and every other tab reads the plainer “Another operator undid the merge at ⟨F⟩”, while a refusal clears only the gesture it refuses.
- **An open menu closes when its offer changes**: the menu is a projection of one snapshot and the room keeps playing under it, so an operator could sit on it and then click a button for a merge that had since been superseded or a ghost that had come back. Every push (and every barrier update) rebuilds this node's markup and compares it with what is on screen; any difference hides the menu. Closed rather than re-rendered in place — the pointer is already on its way to a button, and moving the entries under it would buy a topology change nobody chose. A push that changes only badges or positions leaves the menu alone.
- **Session-lines, frame lines merged at**: "⏪⏪ undo merge here (1 → N lines, merged here as L*n*, L*m*)" → `{mergeEventId, frame}`. The numbers are named as what the REJOIN recorded, not as a promise about what comes back: an absorbed line's number returns to the pool at the merge, so a fork since can be holding it and the undo re-creates the route on the lowest free one (`freeLineId`). The confirm's `landings` name them on the same basis (the caveat covers both — undoing a passage frees the numbers its own cascade took, so they agree unless a fork on an *unrelated* population is holding one; the FRAMES are exact either way), and both lists are sorted by NUMBER, because merge order put the last line to arrive in the middle and one act read `L0, L2, L1` on the button and `L0, L1, L2` in its own confirm. Every line the rejoin absorbed comes back at the frame it left, with its trail and its devices; a device that joined after the merge is spread across the lines coming back, and a restored line nobody came back to lands dormant. Offered for the whole session — whatever the room has built on this population since comes off first, and the label says so (“— also undoes N later steps”), the confirm naming each one — until a room checkpoint rewind expires the merge, after which the menu prints why there is none. The confirm also names **where** they land (`They land L0 → ⟨A2⟩, L1 → ⟨B2⟩, L2 → ⟨C2⟩`, from the server's `landings`) and flags a landing on a hold-until frame, because the undo restores the topology but not the **wait** that produced it: restored lines land un-parked and phase-less, so a barrier-release merge undone leaves its lines standing on the barrier with nothing holding them there. Behind the newest rejoin the ghosts already show this; reaching an older merge draws no route at all, which is exactly where the operator was being asked to commit blind. Three changes finish that thought. The landings are **grouped by destination** — a barrier release parks every line on one frame, so the list came out `L0 → ⟨BARRIER⟩, L1 → ⟨BARRIER⟩, L2 → ⟨BARRIER⟩`, three clauses saying one thing, which reads as the sentence having gone wrong; it is `L0, L1, L2 → ⟨BARRIER⟩` now, and one line per landing is unchanged. The **latecomer clause** distinguishes the devices the operator can see from the ones that registered and left (`— 3 here now, 1 registered but away`, appended only when the two differ): the count is of devices the undo really reassigns, absent ones included, but "4 devices" while three people are playing reads as the tool being wrong. And an older passage's **landing nodes** carry the undo themselves, so it is reachable from where the operator watched the lines walk in and not only from the rejoin frame they have to remember.
- **Session-lines, executed split frame**: "⏪⏪ undo split L*n* here (N lines → 1)" → `{splitEventId, frame}`. Nested descendant splits collapse recursively; descendant timers/waits/sub dives and post-split progress are discarded; every live/map connection and offline registry entry follows the restored parent. A split undo CASCADES exactly as a merge undo does, so the count is the topology the collapse will act on (the children the walk puts back, not the merged line standing there now) and the label carries the same “— also undoes N later steps” hint, the confirm naming each. If a later merge crossed this split's subtree boundary, undoing that merge lifts the block, so the entry is still offered while it is active; the menu explains that the undo is unavailable only once that merge has expired. Split events created before this feature was deployed have no lineage record and therefore cannot be offered retroactively. The entry is gated on the **walk** being possible and not only on the step: a split whose own collapse was fine but which had an expired event standing on it was offered and then refused on the click — and after a room checkpoint rewind that button was the only affordance left on the canvas, so the operator's last apparent route back was a dead one. It now prints the reason instead, in the operator's words (the same table the refusal alert reads), preferring the plan's where there is one because `mixed-merge` names the merge that did the mixing while `blocked-by-expired` only says something in the way expired. A collapse with nothing left to join up reads "(1 line, back to this frame)" rather than "(1 line → 1)", which described a button that does nothing.
- **Session-lines, sub frame**: "⏪ rewind L*n* here" entries for lines **currently inside that sub** whose dive trail passed the frame (each dive's trail is dropped on exit, so only the current dive is rewindable); otherwise a note — "no earlier step of this dive here" when a line IS down in that sub, "no line mid-dive here" when none is.

  **Every "nothing here" note is the fallback of its own section, and prints only when the menu is otherwise empty** (fixed). The advance/eject/rollback entries are built first and kept, so a note can no longer contradict them — which it did on the frame a diver was standing on, where the rewind section is legitimately empty (the trail-end occurrence is the line's current position and is never offered) and the old wording announced "no line mid-dive here" directly under that line's own eject and rollback.

- **Vanilla mode**: one "⏪ rewind here" entry **per occurrence** of the frame in the room's single history (loops make frames repeat) → `MSG_SELECT_HISTORY {selectedIdx}`; the entry for the current position is disabled ("current position"), unvisited and sub-score frames get a note.

**Boot resilience**: the graph fetch retries every 2 s (≤15×, status "score still building — retrying…") before concluding the score has no graph, covering the post-restart rebuild window.

## Operator affordances

- **`⏪⏪` on the frame an undoable split or rejoin happened at**, and **`⏪` on the nodes its lines come BACK to** — the landings a still-undoable passage would restore. Once a passage stops being the newest, the canvas paints no ghost route to those landings either, so the nodes that offer the same one-click undo (`remoteMergeLandingHtml`, and the collapsed entry on a landing a whole convergence shares) carried no marking at all and had to be clicked on spec.
- **Confirms and refusals are in-page panels**, not `confirm()`/`alert()`: structured (the destructive clause gets its own styled line), non-blocking — so the canvas keeps drawing and the panel can invalidate itself when the room moves under it — and cancellable with Escape or a backdrop click.
- **The rewind receipt** is anchored below the barrier strip by measurement (`anchorBelowHeader`), not by a fixed `top`: the strip is in normal flow and comes and goes with the room, and the old constant put the receipt squarely over the strip's right-hand end — which is where the "force advance stragglers" valve lives. It is dismissable (`×`) and dwells 16s. Successful rewinds are also kept newest-first in the session's persisted, 20-entry **rewind log** (the `rewind log` toolbar button), so every operator tab shares the same audit and it survives reloads and server restarts — but **not a score change**, which clears it with the rest of the score-relative state (owner): every entry names a frame of the score being replaced, so carrying it over leaves the map listing rewinds at frames the new score does not have.

## Known limitations & gotchas

- **The map tab is bound to a line but is NOT population** (see decision 3): it cannot hold a line awake, wedge a group/barrier wait, revive a dormant line — those all count `performerLineConnections` only. The binding exists solely so history/graph payloads can be addressed to the tab; no session-lines rewind acts on the _binding_ — the room rewind acts on all non-retired lines and the targeted rewind on the explicitly named line.
- **All session-lines rewinds are map-only in v1** (room checkpoint + targeted line + structural split and merge undos). The session-page history dropdown is read-only in session-lines rooms; it still jumps normally on vanilla scores.
- **A targeted rewind moves only its line** — the registry generation and `latestGroupArrival` stay put, and the "passed ⇒ arrived" excusal means the rewound line replays through track groups the room already passed without waiting (see [session-lines.md](session-lines.md) §8.2 "Targeted per-line rewind").
- **History is an undo trail, not teleport** — only visited frames are rewindable. The structural undos are the explicit exception: they restore a persisted topology snapshot at an executed split or merge instance, never an arbitrary graph node.
- **Boot parses orphan `.subs.json` files as session state** (`loadStoredSessionStates` takes every non-`.html`/`.svg` file): each orphan makes a garbage in-memory `BMSession` that survives only because `buildSVGContent` early-returns on a missing folder. Pre-existing, harmless today, worth a filename filter eventually.
- Chrome "duplicate tab" copies `sessionStorage` → duplicated map tab shares the `did` until refresh.
- Sub boxes auto-fit their children; sub frames are dragged individually (no compound drag).
- The map is operated from a tablet as often as a desktop, so the header controls and every node-menu entry carry a 44px floor, the menu is capped against the viewport (`min(160px, 100vw - 8px)` wide, `100vh - 8px` tall, `overflow: auto`) and its ORIGIN is clamped at both ends — a menu taller or wider than a phone screen used to be placed at a negative offset by the right/bottom clamp alone, scrolling its entries off the top-left corner with no way back.
- **The structural detail tier is a request, not a push** (see Architecture): the map keeps `splitRewinds`/`mergeRewinds`/`absorbedLines` between count pushes and re-asks only when the announced `structuralVersion` changes. An ordinary push says nothing about them, so it must never be read as saying there are none — reading it that way silently emptied every ghost route and structural-undo entry on the canvas. The in-flight mark ages out after 5s, so a reply lost to a reconnect is re-asked for on the next push.
