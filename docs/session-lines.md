## 1. Context

**Why:** Today a Nested Notation session has exactly **one shared playhead** (`BMSession.currentIndex`). Every connected device votes together and advances to the same frame at the same time ([bin/www:332](../bin/www#L332), [database.js:311](../database.js#L311)). **Session Lines** breaks that single-playhead assumption so that, within one session, the flow can **split into multiple parallel "lines"** through the score — each with its own playhead, voting, and holding — then coordinate and re-merge them. Goal: a diverse, simultaneous experience where different participants traverse different routes (and even different sub-scores) instead of everyone being forced down one path.

**Source of truth:** the FigJam "Nested Notation – Session lines" (exported PDF), plus the locked decisions below. The old `feat/session-lines` branch was **explicitly ignored** — the feature was rebuilt from scratch on `feat/session-lines-v2`.

**Out of scope:** "Solving the Sound Transition Problem" (FigJam Section 1) — confirmed not part of this work.

## 2. Glossary

- **Line (flow):** an independent path through the score with its own playhead/voting/holding/history. A session has ≥1 lines.
- **Split:** a frame that divides one line into N child lines.
- **Rejoin / merge:** N lines converging into one at a named frame.
- **Track group:** a named set of frames that wait for each other's lines to arrive **and finish their holding periods** (arrival barrier + hold sync — the group unlocks on the last occupant's hold release), then run time-synchronized voting windows (tallied independently).
- **Hold-until (barrier):** a frame that pauses its line until other named frames have been reached by their lines.
- **Sub-session:** a line temporarily diving into a separate sub-score, isolated, then returning to the main flow.
- **Device:** one connected client (player or rider), identified persistently (see Device identity).

| ---------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `session-split="N"`          | main frame                 | Frame divides its line into N child lines; frame must expose N hrefs. Choice window → personal choice → auto-assign stragglers. A line may split again (nesting allowed).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `session-track-group="name"` | any frame                  | Frames sharing a name **wait for each other's lines to arrive** (arrival barrier — every populated line that can still reach a group frame must land on one; empty lines excluded) **and to finish their holding periods** (hold sync, with 2+ occupants the group unlocks only when the last occupant's hold releases, so the lines leave together; a lone occupant never self-parks), then begin/end voting windows together. | `session-sub-start="Score"`  | `<a>` link in a main frame | The marked link is a **dive**: a line whose advance chooses this link (vote winner, no-vote default, or instant tap) enters sub-score `Score` (at its `START`) instead of moving. Matching is by the link's target frame, so no two of a frame's links may share a target when either is a dive (enforced: `ambiguous-sub-link-target`). |
| `session-sub-end="Score"`    | sub-score frame            | Marks the sub-score's exit. On reaching it, the line pops back to the `href` of the sub-start link it dived through. Self-contained; names no main-score frame.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 4. Locked design decisions

1. **Lines are first-class objects.** Each line has its own playhead, voting/holding state, and history. **Every device is bound to exactly one line** at a time.
2. **Split = personal choice with a bounded choice window** (confirmed). At a `session-split="N"` frame a choice window opens (= voting duration). Each device taps its path and joins that child line. **Non-choosers are auto-assigned at window end to BALANCE line sizes** — keeps lines populated and minimizes empty lines.
3. **`session-track-group` = an ARRIVAL barrier + synchronized timing + independent link tallies + a global STAY override.** **Arrival barrier:** grouped frames don't just vote together — they _wait for each other_. A line landing on a grouped frame **parks** (frame shown, taps ignored — the hold-until banner protocol is reused) until **every populated line that can still reach a group frame has arrived on one** and every arrived line has cleared its own (out-of-group) hold-until. Empty (0-device) lines neither occupy nor are waited for. **"Device" counts every connection — admin included (L3, owner decision): an admin is a player with extra session controls,** so a line occupied only by an admin/SM tab is populated and IS waited for, exactly like any idle player's line; the admin's own tools (tapping the line forward, force-release, or closing the tab so attrition dissolves the wait) are the remedy. _(Exception: score-**map** tabs are observation-only and never population — see §6 Device identity.)_ The wait dissolves **timeout-free via reachability** (a line that goes dormant or navigates off every path to the group stops being "incoming" — same philosophy as #11); the SM force-release valve covers group waits too (panel entry `group:<name>`). A **late arrival** (e.g. a line revived mid-round) is not parked once the group stopped waiting — it joins the running round truncated (decided: lowest-complexity option). SM jumps never park at the landing (authoritative override, like the landing-barrier carve-out). Once released, grouped frames begin/end voting together (first tap opens all windows). Each line tallies independently; for **links**, each line advances to its **own** local winner. **Exception — STAY is group-wide:** at window end take the single largest count anywhere in the group; if it is a _stay_, **all grouped lines stay**; otherwise each line proceeds to its own link winner. (Stay = group-wide brake. Glow marker follows this.) **Tiebreak:** reuse today's random tie-break with leader-stabilization ([bin/www:236](../bin/www#L236)).
4. **Sub-session entry is a chosen link; return is decoupled via that link's `href`.** `session-sub-start` sits on an `<a>` link of a main-flow frame (owner decision — revised from the original frame-level, dive-on-arrival markup): taking that link IS the dive, and the link's `href` is the return landing. The sub-score only marks its own exit (`session-sub-end`) and never references main-score frames. All rejoin/hold orchestration after a sub-session lives on the main-flow landing frame.
5. **Sub-score location:** `public/data/[main-score]/Subscores/[sub-score]/` with its own `Frames/ Sounds/ Documentation/`. Owned by the main score (not a shared library score). **Sub-frames fetched on demand**; main-score frames stay inlined as today.
6. **`session-hold-until` = ALL named frames must be reached** (and each named frame's own holding period ended) before this frame's hold releases. **Rendezvous semantics:** a target counts once **any** line has reached that frame anywhere in the session and that frame's own holding period there has ended — tracked in a persisted session-global `reachedTargets` registry. The waiting line stays parked at its own frame; lines never need to converge on the barrier frame. **Reachability guard:** a missing target keeps the barrier parked only while at least one active, device-bearing, unparked line can still reach it. Dormant, retired, empty, or already-parked lines do not hold a `session-hold-until` target open; once no still-missing targets remain reachable under the current active lines, the barrier releases instead of deadlocking.
7. **`session-rejoin-at` = merge** converging lines into a single line (shared playhead, collective voting resumes) at the target frame. Normally paired with `hold-until` to act as a barrier.
8. **No reciprocal attributes.** Server builds the relationship graph at session-create / score-update; a validation pass runs before a score is used.
9. **v1 sub-sessions are plain** (no nested lines), but the data model + runtime must not preclude nested lines later (high-likelihood future).
10. **Backward compatible.** A score with no `session-*` markup behaves exactly as today: one line = the whole room.
11. **Empty lines go dormant & are revivable.** A line that loses its last device through **attrition** (→ 0 devices) goes **dormant**, not destroyed: it immediately **releases any barrier/rejoin waiting on it** (the awaited frame can no longer be reached — this timeout-free release is the primary deadlock guard) and clears its timers/voting, but **retains its frame, history, `subStack`, and pending coordination** so a later joiner can revive it (see #13). Revival is independent — it brings the line back into circulation (landing per the #13 fast-forward rule; the retained frame is the fallback) and **never re-arms a dependency that was already released**. _Structural_ removals are different: split parents and rejoin-absorbed lines are hard-retired and never selected by normal assignment/revival. The sole exception is an explicit structural undo of that parent's still-recorded split event.
12. **Rider-only lines** (people present, none able to vote) are folded into the nearest votable line (confirmed). A lightweight SM **force-release** remains as a defensive valve.
13. **Late join & path revival.** A device joining (or an unknown `did` arriving) after the room has diverged is assigned via `smallestLineId` over **live votable ∪ dormant** lines (ties → earliest id). A dormant line has 0 devices so it is always the smallest ⇒ newcomers **revive dead paths first**, then balance across live lines. **Revival fast-forward (revised):** a revived line does **not** resume its frozen (stale) position — it fast-forwards to the **latest track-group frame the room has reached** (tracked in a persisted `latestGroupArrival` record, updated on every main-flow grouped landing, cleared on SM-jump rewind), landing on that group's **least-occupied frame** so revivals fill missing track slots instead of doubling covered ones (ties → the recorded arrival frame, then group order). Leaving the frozen frame follows normal departure semantics (it is marked "done" in the reached registry); the landing re-evaluates the group's arrival barrier as usual. Fallbacks to the retained-frame revival of old: no grouped landing recorded yet, the recorded frame no longer resolves/is no longer grouped, or the line froze on a frame of that same group (it already holds a slot — it revives in place). Never assigned to a retired start/parent line. Dormancy already released a line's barriers (#11), so revival is **opportunistic, never a hold** — nothing ever waits for a revive.
14. **No-vote continuation fallback.** When a non-split Session Lines voting window closes with **no valid votes** and no retained in-window vote tally, the line is treated like a line of non-choosers and auto-continues by taking a default outgoing link from its current frame. For Session Lines, a valid vote is either explicit `stay` or one of the current frame's graph-derived outgoing vote ids; stale, malformed, or unresolved link ids are ignored. The default is chosen from the score graph's ordered `frameLinks` for that frame: one valid outgoing link is taken directly; multiple valid outgoing links are tie-broken randomly; no valid outgoing link means no synthetic winner is created and the line remains where it is (terminal/dead-end authoring is handled by validation/operator recovery). Explicit `stay` votes are preserved: if `stay` wins, the line stays. Split windows keep their existing child-line balancing behavior. Track-group windows keep the global STAY brake; if global `stay` does **not** win, a grouped line with no local link winner uses this same default outgoing-link fallback.

## 5. Validation (pre-use)

Scores are validated offline, before use — `lib/session-lines/validate.js`, exposed as `bin/validate-session-lines.js` (`npm run validate-score`, exit code by errors). Running it is the score author's responsibility: the server does NOT validate at build/reload time (a runtime console-only pass existed and was removed as redundant), so an unvalidated broken score fails at runtime (e.g. a wedged barrier), not at load. Checks:

- **`link-unresolved`** (error): every ordinary `<a href>` in the main score and every loaded sub-score points to a frame that exists in that same score (case-insensitive, matching runtime lookup);
- split node's `N` matches its href count;
- every `hold-until`/`rejoin-at`/`sub-start` reference resolves to an existing frame/sub-score;
- **`rejoin-not-linked`** (error): every `rejoin-at` target is one of its frame's own links (the merge is the frame's next step — owner decision; no split×rejoin pairing rule exists, the attributes are independent);
- each `sub-start` score has a `START` and at least one `sub-end`; the marked `<a>` has an `href` resolving to a main frame (`sub-start-no-return` / `sub-start-return-unresolved`);
- **`sub-start-on-root`** (error): legacy root-level `session-sub-start` is refused — the runtime no longer dives on frame arrival, so the old markup would silently do nothing;
- **`split-sub-link`** (error): a `session-split` frame's links are child paths, never dives — land the child on an intermediate frame that carries the sub link;
- **`ambiguous-sub-link-target`** (error): per frame, no two `<a>` may share a target when at least one is a dive. The runtime routes advances by TARGET FRAME (`subLinkForAdvanceTarget`, bin/www) — a pre-Session-Lines design that never sees which `<a>` was tapped — so a shared target is indistinguishable: a plain link + a dive means EVERY advance to that target dives (a tap on the plain link included), and two dives on one target means `find` takes the first and the second sub is unreachable. Both misroute silently in the room. One error per ambiguous target; duplicate plain links (no dive involved) are fine and not flagged;
- **`sub-dead-end`** (error): every landable sub frame keeps a path to a `session-sub-end` (no stranded lines — decided in lieu of a runtime terminal-frame hardening);
- track-group consistency: **`track-group-voting-mismatch`** / **`track-group-holding-mismatch`** (errors) require every frame in a group to use the same `voting` and `holding` attribute values (including all omitting an override and using the session default);
- **`hold-until-in-track-group`** (error): a `hold-until` on a track-grouped frame must not target frames of the frame's own group (the group's arrival barrier already waits for those; out-of-group targets are valid and compose);
- no obviously unsatisfiable barriers (best-effort).

**Deliberate non-check — main-score terminal frames (owner):** a line finishing on a main-flow dead end (e.g. `END.svg`) still counts as "coming" for open barriers; END frames are normal authoring, so a warning would be noise. Recovery is operator force-release or a rewind.

Surface results to the admin console (proposed "Validate score" action) and the dev console, mirroring today's console-based markup checking. **Hook points:** `initState`/`buildSVGContent` ([database.js:240](../database.js#L240), [database.js:345](../database.js#L345)) and `reloadScore` ([database.js:279](../database.js#L279)), invoked from session create/update in [routes/sm.js](../routes/sm.js).

## 6. Data model

Refactor the single-playhead `BMSession` into **session-global state + an array of `BMLine` objects**.

**`BMLine`** (extract today's per-playhead fields from [database.js:174-206](../database.js#L174-L206)):

- `id` (line id, e.g. `L0`, generated on split)
- `currentIndex`, `history`, `historyIndex`
- voting: `isVoting`, `currentBeginTimeStamp`, `currentEndTimeStamp`, `currentVotingDuration`, `votingTimer`, `votingTimeStamp`, `didSendStopVoting`, `currWinningId`, `previousWinningCount`
- holding/standby: `isHolding`, `isStandby`, `currentBeginHoldTimeStamp`, `currentEndHoldTimeStamp`, `currentHoldingDuration`, `holdingTimer`, `standbyTimer`, `nextFrameHoldingDur`
- coordination: `trackGroup` (current frame's group, if any), `isBarrierWaiting`/`isGroupWaiting` (parked at a hold-until barrier / a group arrival barrier), `pendingHoldUntil` (set of frames still awaited), `pendingRejoinAt` (reserved — persisted, never written since the rejoin clarification), `subStack` (stack of `{score, returnHref}` for sub-sessions; stack ⇒ nesting-ready), `savedHistories` (stack parallel to `subStack` — main `{history, historyIndex}` saved on dive, restored on exit), `visitedSubFrames` (qualified `score/frame` visits, so `hold-until="Sub/Frame"` refs are satisfiable), `splitAncestors[]` (ids of the split events this line descends from — powers structural split undo)
- `status` (`'active'`/`'dormant'`; dormant lines stay in `lines[]` so they survive restart and remain revivable — retired lines are structural and never revived normally)
- membership is derived: the set of connections/devices whose `lineId === this.id`

**`BMSession`** keeps the global, score-level fields ([database.js:174-223](../database.js#L174-L223)): `id, ownerId, sessionName, adminPassword, playerPassword, folder, listFiles, listFilesInLowerCase, listMultiChooseImages, soundList, hasSounds, isHtml5, fadeDuration, defaultVolume, defaultAutoplay, enableAutoplayByDefault, votingDuration, holdDuration, votingSize, standbyDuration, synTimeInterval, preloadDuration, isPause, isSessionDeleted`. **Adds:** `lines[]`, `nextLineId`, `graph` (see below), `deviceRegistry` (persistent `deviceId → lineId`), `subFrameCache`, and the persisted coordination registries: `reachedTargets` + `reachedGeneration` (rendezvous, #6 / §8), `latestGroupArrival` (revival fast-forward, #13), `splitEvents[]` (structural split undo, §8).

**Connection tagging** (extend [bin/www:515-520](../bin/www#L515-L520)): keep `sessionId, isAdmin, isStaff, currentVoteTo`; **add `lineId` and `deviceId`** (and `isMapView`, below).

**Device identity:** the server originally had no stable per-device id — a refresh created a fresh connection that just re-read the session's single `currentIndex` ([bin/www:585](../bin/www#L585)). With lines, a refreshed device must rejoin **its** line. The moment a tab reaches the session, the client's `ensureDeviceId()` assigns it a UUID (`crypto.randomUUID()`) and persists it in **`sessionStorage`** (`did`), with an in-memory fallback if storage is blocked; from then on the tab is associated with that UUID. The `did` rides on every message (incl. `MSG_PING`/`MSG_NEED_DISPLAY`); the server keeps `deviceRegistry[deviceId] = lineId` so reconnects restore membership. An unknown `did` is assigned per #13 (smallest live-or-dormant line). `sessionStorage` is per-tab — each tab of one browser is its own performer; `localStorage` would collapse them into one line — and survives refresh and mobile tab-eviction restore; a closed tab mints a new `did` and re-enters via #13. It also keeps the id off every HTTP request and is generated client-side only (never baked into the shared, apicache-cached `${id}.html`). _Gotcha:_ Chrome "duplicate tab" copies `sessionStorage`, so a duplicated tab shares the `did` until refreshed.

**Map connections are observers, not population (owner decision):** the score-map page marks its ws envelope `mapView` → `conn.isMapView`; such connections are excluded from player/rider counts, vote tallies, group/hold-until waits, attrition, dormant revival, adoption parking, split membership and `smallestLineId` balancing (`performerLineConnections` in [routing.js](../lib/session-lines/routing.js) — the only routing helper `bin/www` imports). They keep a line binding only so history/graph payloads can be addressed. A line holding only map tabs goes dormant like an empty one. (Admin _session-page_ connections DO count — L3.)

**A map tab leaves NO footprint at all (owner decision).** Strengthened from "not population" to "invisible", closing the four places a `/map` tab could still be seen: (a) `ensureLineAssignment` returns for a map view **before** the `deviceRegistry` write, so an observer never persists into saved state — where a split's offline-device sweep would have spent one child's balancing slot on it, displacing a genuinely offline performer; a refreshed map tab just re-binds via `smallestLineId`, since the map renders the room from the broadcast `lines[]` snapshot rather than its own line's messages; (b) `countVoteForLine` tallies performers, so a map connection's `currentVoteTo` cannot count even if the page were ever given a way to send one; (c) the admin `lines[]` payload dropped its raw `devices` field — the SM line panel and the map badge both read `players`/`riders`, so no surface shows a number that includes observers; (d) `handleConnectionClose` returns for a map view **before** the attrition grace timer (fixed) — every count already filtered observers out, but the close path did not, so a map tab could still _start_ a dormancy window. Reachable, and verified by A/B in a browser: a device that goes offline before a split still gets a child line from the offline-device sweep, leaving that line **active with zero performers and no timer**; the map binds exactly there (`smallestLineId` picks the emptiest), and closing or reloading it made the absent performer's line go dormant. Broadcasts (`sendToAllClients`/`sendToLine`) and the `currentVoteTo = -1` resets still reach map tabs: the first is what the page is for, the second is a no-op on a connection that never votes.

**Relationship graph** (built in `buildSVGContent` / on reload, [database.js:345](../database.js#L345)): while reading each frame, additionally parse the `<svg>` root for `session-*` attributes and record: split nodes (+N + their hrefs), track-group membership, hold-until targets, rejoin targets, sub links (`subLinks`: frame → `[{score, returnHref}]`, parsed from `<a>`-level `session-sub-start`) and sub-end (→ score) mappings, plus per-frame ordered link targets (`frameLinks`). Produce a normalized model the runtime consults (no reciprocal attributes needed). _As built:_ the graph is **not persisted** — it is re-derived on every build/boot (the `toJSON` allowlist drops it), and it is assigned for **every** score, vanilla included (the [score map](score-map.md) presents a vanilla score as a single-line session); orchestration still gates on `hasSessionLines`, which is set only when `session-*` markup exists.

## 7. Runtime lifecycle

All voting/holding functions in [bin/www](../bin/www) take a `line` within a `session` (formerly just a `session`). Messaging helpers have a per-line variant (`sendToLine`, filter on `conn.lineId`).

1. **Session start.** One line `L0` at a `START`/`PRE` frame ([database.js:294](../database.js#L294)). All devices join `L0`. Identical to today until a split occurs.
2. **Line-scoped voting.** `countVoteForLine`: tally `conn.currentVoteTo` only over connections with `conn.lineId === line.id` ([bin/www:213-252](../bin/www#L213-L252)). `startVoting/stopVoting/holding` operate on the line; `MSG_BEGIN_VOTING`, `MSG_UPDATE_VOTING`, `MSG_SHOW`, `MSG_BEGIN_HOLDING` are sent only to that line's connections. Session Lines only counts `stay` or link ids matching the line's current outgoing links; stale/malformed link ids are ignored. If a non-split line closes with no valid votes and no retained `_lastVoteCounts`, `countVoteForLine` synthesizes a `winningVoteId` from the current frame's ordered outgoing links (`graph.frameLinks[frameNameForLine(session,line)]`) so the line auto-continues instead of falling back to `currentIndex`; no valid outgoing link leaves it in place (#14).
3. **Split.** Line reaches a `session-split="N"` frame → open a choice window (voting-duration based). Devices tap → recorded as their chosen child path. At window end: create N child lines, distribute choosers to the child line matching their tap, **auto-assign non-choosers** (balance/default, `planSplitPartition`), and hard-retire the parent while the split remains active. The split instance is persisted (`splitEvents[]`); children carry its id in `splitAncestors[]`. From the score map an admin may structurally undo it (§8). **A split frame has no winning vote** — the line divides, so no single link is "the" outcome; `MSG_UPDATE_VOTING` there drops the shared `winningVoteId` and is addressed per device with that device's own destination instead (§11).
4. **Track group.** _(a) Arrival barrier:_ a line landing on a frame in group G parks (`isGroupWaiting` via `maybeParkAtGroup`; the hold-until banner protocol `MSG_BARRIER_WAITING`/`RELEASED` is reused — zero client change) while any populated line that can still reach a G frame hasn't arrived, or any arrived line is still hold-until-blocked. The wait is re-checked on every landing, dormancy, hold-until release, SM jump and post-restart rehydration (`canReachFrames` BFS over `graph.frameLinks` + pure `groupArrivalState` in the orchestrator; `tryReleaseGroupWaits` in bin/www; empty lines excluded; sub lines project to their return landing) and releases all parked G lines together — no timers. First device joining an empty/dormant line on a G frame re-parks it (`ensureLineAssignment`); a line arriving after the group released joins the running round truncated; group-parked lines are excluded from a round's resolution sweep. _(b) Synchronized voting:_ when any unparked line whose current frame is in G starts voting, the server starts the voting window for **all** lines currently sitting on a frame in G (synchronized start/end; parked lines excluded). Tallies remain per-line. At close, a global-max `stay` still makes every grouped line stay; otherwise each line takes its own link winner, falling back to its own default outgoing link when it has no local link winner. _(c) Split composition (S7):_ a grouped `session-split` frame still **divides** its line when the group advances — the group close delegates it to the split path (choosers land on their tapped child, stragglers are balanced across the children), never a whole-line link/default advance; a global `stay` brakes it un-split like any other grouped line. The group check runs **before** the split check at window close, so the outcome does not depend on whose synchronized window closes first.
5. **Hold-until (barrier).** On arrival at a `hold-until="X,Y"` frame, the line enters holding with `pendingHoldUntil={X,Y}` and the barrier-waiting banner (`MSG_BARRIER_WAITING`). The server marks targets satisfied as lines reach X and Y (and finish those holds). When the set is empty, release the hold (`MSG_BARRIER_RELEASED`) and proceed. If a target remains missing but no active, device-bearing, unparked line can still reach it (main-flow reachability, or qualified sub-score reachability via `Subscore/Frame.svg` — `tryReleaseBarriers` / pure `holdUntilReachabilityState`), it no longer keeps the barrier open; the barrier releases once no still-missing targets are reachable. _(Rendezvous: "reached" lives in the persisted session-global `reachedTargets` registry — `arrived` on landing, `done` when that frame's own hold ends; barriers release on `done`. On release, a single paired `rejoin-at` target auto-advances + merges the released lines there; multiple targets are left to the line's route vote, with the merge happening on arrival.)_
6. **Rejoin (merge).** When a line navigates to a `rejoin-at` target frame, it merges with any other line already designated to rejoin there: pick/keep one surviving line (`planRecombine` — survivor = lowest id, keeps history), reassign the other lines' devices (`conn.lineId`, `deviceRegistry`) to it, **hard-retire** the absorbed lines (structural — not dormant/revivable). Collective voting resumes on the merged line. Merging is by **co-presence** — no waiting; a score that needs a guaranteed merge pairs the target with `session-hold-until`.
7. **Sub-session (decoupled).** A line's advance choosing a `session-sub-start="S"` link — vote winner, no-vote default, grouped link winner, or instant tap (`subLinkForAdvanceTarget` at each navigation call site; matching is by the link's target-frame index, which vote ids and default fallbacks carry) — dives instead of moving: push `{score:S, returnHref:<the link's href>}` onto the line's `subStack`, save the main `{history, historyIndex}` onto `savedHistories`, load sub-score `S` frames on demand, set the line to `S/START` (`MSG_SUB_ENTER`). Rewinds, revival fast-forwards and other repositions never dive (they are not navigations). The line runs isolated (own voting/holding; no cross refs); frames visited inside record qualified `score/frame` entries in `visitedSubFrames` (this is what satisfies qualified `hold-until` refs). On reaching a `session-sub-end="S"` frame: pop the stack, restore the saved main history (the return landing is appended on top), set the line to `returnHref` in the main flow (`MSG_SUB_EXIT`). Stacks support future nesting.
8. **Attrition & revival.** When a line's last device leaves (attrition → 0 devices) the line goes **dormant**: release any barrier/rejoin awaiting it (#11), clear its timers, but keep its `currentIndex`/history/`subStack`/pending coordination. **Attrition is debounced by a grace window** (`ATTRITION_GRACE_MS`, ~8 s): dormancy and its barrier releases only finalize if no device reclaims the line in time, so a page refresh or a mobile network blip (the ws reconnect backoff is 1–5 s) can't irreversibly dissolve coordination. `ensureLineAssignment` cancels the timer on any (re)assignment; it includes dormant lines as targets (count 0 ⇒ smallest ⇒ revived first, #13); assigning a device flips it back to **active**, landing per the #13 fast-forward rule (retained frame = fallback). Split-parent and rejoin-absorbed lines remain unavailable to this normal revival path (retired lines are excluded from registry lookups and assignment fallbacks; a split sweeps offline `deviceRegistry` entries off the parent); structural split undo restores its specific parent explicitly.

## 8. History & rewind

Session-lines rooms have **three rewind operations, all map-only in v1** (the session-page history dropdown is a read-only trail display there — `available:false` always; the implicit bound-line `{selectedIdx}` jump was retired and is refused server-side). Vanilla scores keep the single-playhead per-step `MSG_SELECT_HISTORY {selectedIdx}` jump — their one playhead IS the room. See [score-map.md](score-map.md) for the menu UX.

**History is an undo trail, not teleport** — only visited frames are rewindable (structural split undo is the explicit exception: it restores a persisted topology snapshot). A landing that doesn't move the line (e.g. a room rewind that keeps it in place) does not append a duplicate trail entry (`setCurrIdxTo` skips the push when the trail already ends with the landing frame); any landing also heals trailing duplicates left by older sessions. Rewinds carry a **caller invariant**: whoever sets `historyIndex` externally must land the playhead on `history[historyIndex]` itself — every rewind path derives its landing frame from that trail entry, and `setCurrIdxTo` warns if one ever stops doing so.

### 8.1 Room-wide checkpoint rewind — `MSG_SELECT_HISTORY {group}`

Track groups act as **synchronized checkpoints** (FigJam reading (i): when diverged positions make plain history impossible, the room-wide rewind offers synchronized track groups as jump targets — a rescue tool, not a disabled control). Click or tap a common checkpoint group frame on the map → the server recomputes checkpoints on receipt (never trusting the client's list) and moves **every non-retired line** to its own landing in that group (`roomRewind` in bin/www; pure `commonCheckpoints`/`roomRewindPlan` in the orchestrator).

Semantics:

- **Checkpoint** = a track group for which EVERY currently-populated line's trail contains one of the group's frames. Groups passed by only some lines are NOT checkpoints. All common checkpoints are offered, newest-first (not only the latest); with loops, only each line's latest occurrence per group counts (v1).
- **Landing rule per line:** its own most recent trail occurrence of a frame of the target group (history truncates via `setCurrIdxTo`). Lines with no such entry (e.g. a child born later) land on the group's **least-occupied frame** (same occupancy logic as revival, `revivalLandingFrame`).
- **Mid-sub lines** are force-exited from their dive first (saved main history restored), then the landing rule applies. **Dormant lines** are repositioned like any other but stay dormant.
- **Availability:** admin-only; requires ≥1 common checkpoint; deliberately NOT gated on any history-availability predicate — rescuing a diverged/wedged room is the point.

**Registry on rewind — generation counter (option (b)):** an SM rewind bumps `session.reachedGeneration` and restarts `reachedTargets`, so every barrier met **after** the rewind — including ones satisfied before it — gates like a first pass. Carve-outs and details:

- The barrier **at** the rewind landing is already unlocked (the room passed it): the rewind pre-satisfies the landing frames' own hold-until targets (for the room rewind, the union across ALL landing frames, in one generation restart).
- Rewinding a **parked** line un-parks it (clears `isBarrierWaiting`/`isGroupWaiting`/`pendingHoldUntil`, drops it from the barrier entry) and sends `MSG_BARRIER_RELEASED` so the client's "waiting for other lines…" banner is dismissed.
- Landing on a frame with `session-sub-start` links needs no carve-out — dives are navigation-triggered, so any reposition leaves the line sitting un-dived; its next vote may choose the sub link (diving properly) or another link.
- Landing on a grouped frame **never parks** (authoritative override) and re-checks group waits the line was incoming to.
- `latestGroupArrival` restarts with the registry, then the rewind's own **grouped landing immediately re-arms it** (the rewind is the room's newest position of record — a checkpoint rewind always lands on a group, so revivals fast-forward there).
- _Self-healing, accepted:_ after the registry restarts, other lines' _current_ positions are not re-seeded into the fresh generation — a barrier whose target frame someone is already standing on sees it covered only when that line next moves (departure marks the frame done).

### 8.2 Targeted per-line rewind — `MSG_SELECT_HISTORY {lineId, selectedIdx, frame}`

An admin may rewind **one named line** to an earlier entry of its own ACTIVE trail (undo, not teleport) — on the main flow, or within its current sub dive ("a sub is a session of its own"). Admin-only; `frame` is a race guard (refused if the trail entry moved). Implementation (`lineRewind` in bin/www): resolves against the line's active frame list (sub-aware), cancels its timers, un-parks + banner-releases — and deliberately does **NOT** restart the rendezvous registry nor touch `latestGroupArrival` (the ROOM did not rewind).

- **Track-group rule: passed ⇒ arrived.** A line whose trail already went through a group is never counted as "incoming" again, so a line rewound behind the group replays through it without waiting for the lines ahead (its own truncated trail makes it re-arrive for real). Implemented as the `hasPassed` excusal in `groupArrivalState`, wired to `mainTrailForLine` (on forward-only scores reachability already excluded the ahead lines; `hasPassed` makes the rule hold with loops).
- **Scope:** rewinding a line OUT of its sub is out of scope (room rewind force-exits subs). Map menu offers per-past-trail-occurrence entries on main frames (main-flow lines) and sub frames (lines currently in that sub).
- **Known interaction (verified, accepted):** the rewind leaves `latestGroupArrival` alone, but the line's NATURAL landings while replaying re-arm it (#13 — every main-flow grouped landing is the room's newest of record), so a dormant line revived during the replay window fast-forwards to the replayer's group, not the front of the room.

### 8.3 Structural split undo — `MSG_SELECT_HISTORY {splitEventId, frame}`

Rewinding an executed split collapses every current descendant **recursively** back into the original parent at that split node. Unrelated lines keep their reached/checkpoint state; the reached registry and `latestGroupArrival` are untouched (a subtree rewind, not a room rewind). Descendant timers/waits/sub dives and post-split topology are discarded; connections **and** offline `deviceRegistry` entries are rebound to the restored parent; parent history restored. Descendant-only later splits/merges are included; a merge crossing outside the target subtree **permanently blocks** that split's undo (populations can no longer be separated) — only the crossed split event is marked blocked. `splitEvents[]` is append-only (`active` → `undone`), so repeated visits to the same frame remain distinct across restart. `frame` is the race guard. Events created before this feature was deployed have no lineage record and cannot be offered retroactively.

### 8.4 Recovery tools, in general

Force-release and rewind split cleanly: **force-release = skip the wait** (irreversible — per #11 a released barrier never re-arms); **rewind = replay and satisfy the wait properly** (re-opens closed paths, possibly taking the route to a missed target this time). "Unreachable" is never permanent while the rewind tool exists.

## 10. Session manager controls across lines

- **Pause / global refresh:** session-global, apply to all lines (as today, [bin/www:658-680](../bin/www#L658-L680)).
- **Hold:** SM hold needs a scope decision (all lines vs a chosen line) — TBD with SM-UI work.
- **History / rewind:** the three map rewinds of §8; session-page dropdown read-only for session-lines rooms; vanilla keeps its per-step jump.
- **Force-release valve** (decision #12): admin force-release for a stuck barrier, incl. group waits (panel entries `group:<name>`).
- **SM visibility (implemented):** per-line device counts / frame occupancy ship two ways: the line-distribution panel on the session page (admin-only, `payload.lines` on `MSG_SHOW_NUMBER_CONNECTION`, refreshed on every line landing), and the standalone **live score map** (`/session/:id/map` — full score DAG with per-line badges, barrier/sub state, history trail and a click/tap rewind menu; works for vanilla scores as a single line). See [score-map.md](score-map.md).
- **Stuck-wait valves (implemented):** a waiting barrier offers the operator two opposite resolutions, in the session page's `#admin-barrier-panel` **and** in the map's `#session-map-barriers` strip, which is where a stall is actually watched developing. **release** / **release all** let the barrier go without the lines it is waiting for (the original decision #12 valve). **force advance** / **advance all stragglers** do the reverse: each straggler teleports onto the group's least-occupied frame — the same landing rule a dormant-line revival uses (decision #13 revision), so forced arrivals fill empty track slots instead of doubling covered ones — and the now-full group releases down the ordinary path. Advancing is `confirm`-gated (it moves performers' devices) while releasing is not. A forced arrival is still an arrival: if the group is _still_ waiting on someone else, the line just brought in parks with the rest. The map also badges a straggler line `⏩` against a parked line's `⏳`. Note a force-release is the one release with no landing behind it, so it explicitly re-pushes the per-line snapshot — without that the panel and badges kept showing the wait the operator had just resolved. `finalizeAttrition` needed the same push for the same reason: the ws close handler pushes immediately, but dormancy lands 8 s later on a timer, so the panel kept a line listed as active and still-waited-on well after both stopped being true.
- **The panel's `stragglers[]` is computed before the payload is built**, not after: `notifyAdminsBarriers` opens by calling `refreshStragglerNotices`. Refreshing afterwards left the panel exactly one edge behind, which is invisible in steady state and obvious after a restart — devices reconnect one at a time, each reconnect changes who is being waited on, and the panel would name only whoever reconnected first while the line panel (a different payload) named everyone. For the same reason a **player** reconnect re-pushes the panel; the admin-only push further down fires only for admins.

## 11. Client & display changes (verified against client code)

The client renders whatever frame/voting state the server addresses to it, so **most client code is line-agnostic** — the bulk of the work is server-side per-line addressing, plus these targeted client changes:

- **Per-line show needs no client change.** `parseMessage` ([session.js:56](../public/javascripts/session.js#L56)) handles `MSG_SHOW`→`showImageAtIndex` ([session.js:312](../public/javascripts/session.js#L312)), which shows `#MainContent svg[id="svgN"]` and hides the rest. The client just shows whatever index its line is told.
- **Stay/winning glow needs NO client change.** The glow follows the server's `winningVoteId` ([voting.js:111](../public/javascripts/voting.js#L111); [voting.js:201](../public/javascripts/voting.js#L201) already handles `winningVoteId==="stay"`). The whole stay rule is implemented server-side by setting each line's `winningVoteId`.
- **Split frames replace that one glow with a per-device destination marker.** A `session-split` frame has no winner to glow, so the server sends no `winningVoteId` there and hands each device `splitDestinationVoteId` — the child link it is currently going to. The client marks it with the same look the winner has (`winning`, plus a `destination` class as the DOM/QA hook), which is what a **play-mode** device sees: it cannot tap, so this marker is its only cue about where it is being sent. The marker is shown for the **whole** window, in both modes — including after the performer taps. A first cut dropped it once it equalled the device's own vote (on the reasoning that `current-vote` already marked that link); in testing that read as the app losing track of the device the instant it was guided, so the two now **stack** on the one link — `vote-indicator current-vote destination winning` — saying both "my choice" and "where I land".
- **Chosen and assigned destinations are told apart by colour.** A destination the device did **not** choose was placed by the server's balancing, so it renders **blue** with an **"auto"** label in the middle of the circle; a path the performer tapped keeps the orange of an ordinary vote. Colour is the _only_ difference, and it is enforced structurally: `.vote-indicator` declares `--marker-ink` (border + text) and `--marker-glow` (pulse/gradient, as raw RGB channels so stops can vary the alpha), every shared rule and both keyframe sets read those variables, and `.vote-indicator.auto` re-points them and nothing else. A first cut instead duplicated the play-mode rule with a blue gradient — and the `background` **shorthand** in it silently reset the `background-repeat`/`position`/`size` that the orange rule sets in the three declarations right after its own shorthand, so the blue glow tiled from the top-left instead of pulsing from the centre. Duplicating the rules is what made that possible; sharing them makes it unrepresentable. Every play-mode device is in the auto case (it cannot tap), as is a guide-mode device that has not chosen yet. The label is always in the DOM and its legibility is left to CSS — play mode's `color: transparent` hides it — because switching modes never re-renders these indicators, so a JS mode test would go stale the moment the performer toggled guide mode. When the assigned link also carries votes, the count and the label stack inside the circle (`.vote-count` + `.auto-label`, `flex-direction: column`). Because the destination is an assignment, not a tally, it is marked even on a link with zero votes: an indicator with no count is injected for it and survives the "remove everything not in the dic" sweep.
- **Indicator positioning was broken and is fixed (pre-existing, all scores).** `injectVoteIndicator` assigned bare numbers to `style.top`/`style.left`; a CSS length without a unit is an invalid declaration, so the CSSOM dropped it and every injected indicator fell back to the stylesheet's `top/left: 0` — piling every vote bubble and the winning glow into the viewport's top-left corner instead of over its link. Now `` `${…}px` `` (verified headless: the indicator's centre lands exactly on the link's centre). This affects vanilla scores too; it is not session-lines-specific.
- **The destination moves during the window, on purpose.** Non-choosers are balanced across the children, so one performer's tap can re-balance another device's slot; the marker follows the live partition exactly as the winning glow follows the live tally. It is pushed the moment the window opens — **with the tap that opened the window already counted** (`startVotingForSessionWithDelay`'s `initiator`, which survives the reset of the previous window's votes), so the tapper is never told it was auto-assigned somewhere its own echo is about to overwrite; everyone else is a straggler, spread evenly, so nobody stares at an unmarked frame — and again from `resolveSplit` off `applySplit`'s **own** assignment, so the last marker a device sees before the frame changes is always the child it actually got.
- **Device identity.** `ensureDeviceId()` on session load (§6); `did` added to every `sendToServer` envelope ([ws-client.js:148](../public/javascripts/ws-client.js#L148)). The reconnect path already re-pings ([ws-client.js:44](../public/javascripts/ws-client.js#L44), [ws-client.js:70](../public/javascripts/ws-client.js#L70)), and `sessionStorage` persists across refresh/eviction restore, so membership restores automatically.
- **Split tap** reuses `handleSelectLink`→`MSG_TAP` ([voting.js:33](../public/javascripts/voting.js#L33)); the server interprets taps as line choices during the split window (optional "choose your path" labeling). Client handles `MSG_LINE_ASSIGNED` (stores its own line).
- **Barrier banner:** `#barrier-waiting-indicator` + body class, driven by `MSG_BARRIER_WAITING`/`MSG_BARRIER_RELEASED` (also reused by group-arrival parking). It carries **two roles**, stamped as `data-role` and sharing the one clear signal: `parked` → "waiting for other lines…" for a line held at a hold-until or group-arrival barrier, and `straggler` → "Your move, proceed when ready…" for a line a waiting group is held open **for**, which until then was told nothing at all and so never knew the room was standing still on its account. The straggler prompt is styled in the app's accent (it asks for an action) while the parked banner keeps the passive grey it shares with the loading indicator. **Both are guide-mode only** (owner): they are navigation messages, and in play mode they merely sat over the frame a performer was sounding. Visibility is a stylesheet rule on `.guide-mode … [data-role]`, never an inline `display` — switching modes does not come back through the JS, so a mode test there would go stale the instant a performer guided their device.
- **Who is a straggler** is the group's `incomingIds` minus the lines that are themselves parked (pure `orch.groupStragglerIds`). A parked line stays in `incomingIds` — the group really is waiting on it, and dropping it would release the group early — but it cannot proceed, so "your move" would be a lie and its own banner already explains the wait. Blocked _occupants_ (`blockedIds`) are never stragglers: they have arrived; the group waits on their hold, not their travel. The flag rides on `line.isGroupStraggler`, which is transient (absent from BMLine's persistence allowlist) and re-derived from live positions on every barrier edge.
- **Sub-frames.** Fetch + inject per §9; audio `registerSubFrames` + `getSoundLink(name, ctx)`.
- **SM live controls** (hold/pause/history/global-refresh) live in the **session page** admin UI ([session.js:28-41](../public/javascripts/session.js#L28-L41)), not `routes/sm.js`.

## 12. Server message protocol

- `sendToLine(line, time, payload)` (+ `…WithDelay/…Admins` variants; filter connections by `conn.lineId`); keep `sendToAllClients`/`sendToAllAdmins` for session-global messages (`PAUSE/GLOBAL_REFRESH/CHECK_HOLD/SHOW_NUMBER_CONNECTION/FINISH`).
- `MSG_PING` / `MSG_NEED_DISPLAY` carry `deviceId`; server resolves `lineId` via `ensureLineAssignment` and replies with that line's current frame/voting/holding state ([bin/www:585-629](../bin/www#L585-L629)).
- `MSG_TAP` is line-scoped, plus the split-choice path.
- `MSG_UPDATE_VOTING` is line-scoped (`sendVotingUpdateToLine`), **except on a split frame**, where it is per connection: `countDic` carries no `winningVoteId` and each payload gains `splitDestinationVoteId` — the vote id (`target#frame#slot`, built by the pure `orch.splitDestinationVoteIds`, so it is the id that link's `<a>` actually carries) of the child that device is going to, or `null` for a connection outside the partition. Sent to performers only; the map page ignores the message. Vanilla and non-split payloads are unchanged — the field is simply absent.
- New constants ([constants.js](../constants.js), wired through the jade `fn({...})` in [database.js:439-454](../database.js#L439-L454) and the `window.MSG_*` block in [session.jade:41](../views/session.jade#L41)): `MSG_LINE_ASSIGNED=16, MSG_BEGIN_SPLIT=17, MSG_BARRIER_WAITING=18, MSG_BARRIER_RELEASED=19, MSG_SUB_ENTER=20, MSG_SUB_EXIT=21`.
- `MSG_SELECT_HISTORY` payload variants: `{selectedIdx}` (vanilla jump; refused for session-lines rooms), `{group}` (room checkpoint rewind), `{lineId, selectedIdx, frame}` (targeted line rewind), `{splitEventId, frame}` (structural split undo).
- `MSG_BARRIER_WAITING` payload variants: `{frame, targets}` / `{frame, group}` (this line is parked), `{frame, group, straggler: true}` (a group is waiting for this line), and the admin-flagged `{admin: true, barriers[]}` — each barrier carrying `frame` (a hold-until frame name, or `group:<name>`), `targets`, `parked[]` and `stragglers[]`.
- `MSG_BARRIER_RELEASED` is dual-use: outbound it clears whichever banner a line is showing; **inbound from an admin** it is the operator's valve — `{frame}` resolves one barrier, no frame resolves every waiting one, and `{advance: true}` picks the opposite resolution (bring the stragglers in rather than let the group go without them).

## 13. Persistence & restart

`saveSessionStateToFile` serializes via a versioned `toJSON()` **allowlist** (v1 flat → v2 `lines[]`; `migrateState` upgrades old files): `lines[]` (timers nulled, `isVoting` false; `BMLine.fromJSON` rehydrates — persisted fields include `isBarrierWaiting`, `pendingHoldUntil`, `subStack`, `savedHistories`, `visitedSubFrames`, `splitAncestors`, `status`), `deviceRegistry`, `reachedTargets`/`reachedGeneration`, `latestGroupArrival`, `splitEvents[]` — dropping re-derivable `listFiles*`/`graph` ([database.js:519-536](../database.js#L519-L536), [database.js:629-648](../database.js#L629-L648)). On restart, rebuild lines and graph; **barrier state survives**: a lazy `rehydrateBarriers(session)` rebuilds the transient `_barrier` map from persisted line state on the session's first message after a restart, then schedules a deferred `tryReleaseBarriers` after the reconnect grace window (an immediate check would see zero reconnected devices and force-release); group waits are re-checked on rehydration too. Reconnecting devices restore their line via `deviceId`.

**Writing the file is durable.** Saves are queued per session and published atomically (temp file + rename), because `fs.writeFile` truncates at open and writes afterwards: two overlapping saves used to interleave, leaving the longer payload's tail past the end of the shorter one's JSON and a state file the next boot could not parse. Boot is fault-tolerant to match — `loadStoredSessionStates` reads `${id}.json` only (never `.subs.json`, a rendered `.html`/`.svg`, or a `.json.tmp` leftover), and a file that still fails to parse is renamed to `.corrupt-<ts>` and skipped with a `console.error` instead of taking every other session down with it ([database.js](../database.js), [test/state-file.test.js](../test/state-file.test.js)).

## 14. Implementation architecture (as built)

Delivered incrementally on `feat/session-lines-v2` (chunks A–N: test harness/baseline → parser/graph/validator → graph wiring → `BMLine`+shim+versioned persistence → per-line messaging/device identity → per-line voting/holding → orchestrator → split → hold-until/rejoin → sub-sessions → track groups → SM controls → cleanup), under these standing principles:

1. **Gate everything** on `session.hasSessionLines`. A score with no `session-*` markup stays **byte-for-byte identical** in built output and behavior (proven continuously by a baseline snapshot diff of a vanilla score's `server_state` output).
2. **Pure logic in `lib/session-lines/`** — `parse.js` (frame-attr parser), `graph.js` (`buildGraph`), `validate.js`, `routing.js` (`sessionConnections`/`lineConnections`/`performerLineConnections`/`smallestLineId`), `orchestrator.js` (`planSplitPartition`, `holdUntilSatisfied`, `groupArrivalState`, `holdUntilReachabilityState`, `planRecombine`, track-group window helpers, `subReturnIndex`, `createOrchestrator(transport)`) — no express/ws requires, unit-testable without booting servers.
3. **Single-line invariant:** until a split happens, all new code reduces to today's behavior (`lines[0]`); a prototype accessor shim let `bin/www` be converted incrementally.
4. **Test harness:** dependency-free Node scripts in `test/` (`node:assert`, `test/run.js`, `npm test`; Node 14+), plus offline tools `bin/build-score.js <folder>` and `bin/validate-session-lines.js`.

**Critical files:** [database.js](../database.js) (BMSession/BMLine, graph build, versioned persistence, sub-frame build), [bin/www](../bin/www) (per-line voting/holding/messaging, split/barrier/rejoin/sub/group orchestration, device identity, rewinds), `lib/session-lines/*`, [routes/session.js](../routes/session.js) (sub-frame + map/graph routes), [routes/sm.js](../routes/sm.js) (graph-build + validation hooks on create/update), [constants.js](../constants.js), client: [views/session.jade](../views/session.jade) (`#SubSessionContent`, MSG wiring), [public/javascripts/session.js](../public/javascripts/session.js), [ws-client.js](../public/javascripts/ws-client.js), [voting.js](../public/javascripts/voting.js), [audio-player.js](../public/javascripts/audio-player.js); score map: see [score-map.md](score-map.md).

## 16. Open items & known issues

**Parked (open design items):**

- **Vote-marker glow** follows the resolution rule (group stay-leader vs per-line link-leader); exact rendering to verify against client code. _Split frames are settled: no shared winner, a per-device destination marker instead (§11)._
- **SM hold scope** across lines (all vs chosen line) — with SM-UI work.
- **Multi-exit sub-scores** (several `sub-end` frames → different main landings) — extension to the decoupled href mapping.
- **Session-page rewind UX:** the map's checkpoint / targeted-line rewinds could later also be offered from the session-page dropdown (modal design pending).
- **L5 (from the code review, Appendix A — accepted approximation):** group resolution edge cases — grouped lines that were _not_ voting when the group resolves get forced into standby + a stay-glow `MSG_UPDATE_VOTING`, and a line arriving at a grouped frame mid-window opens its own later window, so a group can resolve twice. Acceptable approximation of "begin/end together"; revisit if it bites.

- **Forcing a line out of a sub-score needs `MSG_SUB_EXIT`, not `MSG_SHOW`**. Only the _natural_ sub end (`exitSubSession`) sends it, yet three paths pop `line.subStack` server-side and then push a bare `MSG_SHOW` carrying a **main-flow** index. The client's sole exit from sub view is the `MSG_SUB_EXIT` handler ([session.js:291](../public/javascripts/session.js#L291)), so those devices keep the sub's injected frame list and `frameContext`: `showImageAtIndex` looks for `sub-<name>-<idx>`, finds nothing, the display goes blank on a stale frame and the audio player throws `Cannot read properties of undefined (reading 'noteIds')` on the unresolvable id. `forceAdvanceStragglers` sends it (and, while paused, re-sends `MSG_PAUSE` so the stale sub context cannot outlive the move and break the eventual unpause). `roomRewind` sends it too (fixed, same shape: capture `wasInSub` **before** unwinding `subStack`, then `MSG_SUB_EXIT` — plus a re-sent `MSG_PAUSE` while paused — instead of the main-flow `MSG_SHOW`, which the non-dived lines still get). Verified in a browser by A/B on a fixture whose track group sits _before_ the subs: with the fix every line returns to `frameContext.type === "main"` on its group frame; with it disabled the main-flow index resolved against the **sub's** injected list, so each device sat on an unrelated sub frame (`domId` still `sub-<name>-<idx>`) while the server believed the line was on the group frame — a silent desync, and the renderer wedged hard enough that a CDP screenshot timed out. `fastForwardRevivedLine` has it too but is unreachable in practice: a revival is triggered by a device _joining_ a 0-device line, so its page is freshly loaded and never in sub view.
- **Two copies of the parked banner text.** [session.jade](../views/session.jade#L140) ships `#barrier-waiting-indicator` with "waiting for other lines…" baked in, while `BARRIER_BANNER_TEXT` in session.js is what actually renders (the JS always sets `textContent` before showing a role). The jade copy is dead content — a device that never receives a barrier message simply carries it hidden — but it reads like the source of truth. Left alone deliberately: session.jade is the vanilla template, so editing it moves the byte-identical baseline.
